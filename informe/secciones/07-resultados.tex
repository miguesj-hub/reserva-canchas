\section{Resultados}
\label{sec:resultados}

\subsection{Funcionalidades implementadas}
\label{sec:funcionalidades}

En la versión actual del proyecto se encuentran implementadas las funcionalidades
principales definidas para el usuario final y el administrador. Los recorridos
pueden realizarse desde los microfrontends y utilizan los servicios del backend
correspondientes para completar cada operación.

\begin{itemize}
    \item \textbf{Reserva y cancelación por parte del usuario final.}
    Se permite el registro e inicio de sesión, la consulta de disponibilidad
    por deporte, cancha y fecha, y la selección de un bloque horario libre.
    Una vez creada la reserva, esta aparece en la sección de reservas del
    usuario y puede cancelarse mientras todavía no haya comenzado. Al cancelar,
    el bloque vuelve a mostrarse como disponible.

    \item \textbf{Administración de canchas y reservas.}
    El administrador puede crear y editar canchas, cambiar su estado entre
    activa e inactiva y gestionar bloqueos de mantenimiento. También dispone
    de un listado global de reservas desde el cual puede cancelar reservas de
    cualquier usuario, siempre que todavía cumplan las condiciones de
    cancelación establecidas por las reglas de negocio.

    \item \textbf{Reportes de uso.}
    El módulo de reportes permite seleccionar un rango de fechas y consultar
    los cuatro indicadores definidos para el proyecto: número de reservas por
    cancha y deporte, porcentaje de ocupación por cancha, número de
    cancelaciones y ranking de canchas según su demanda. El panel de
    administración utiliza estos mismos datos para mostrar un resumen
    correspondiente al día actual.

    \item \textbf{Gestión de usuarios.}
    El administrador puede consultar las cuentas registradas y cambiar su
    estado entre activo e inactivo. Cuando una cuenta se inactiva, sus reservas
    se conservan. Si el usuario mantenía una sesión abierta, la siguiente
    petición autenticada es rechazada, debido a que el API Gateway vuelve a
    validar las credenciales en cada solicitud. Ante este caso, la interfaz
    elimina la sesión almacenada y devuelve al usuario a la pantalla de inicio
    de sesión.
\end{itemize}

El proyecto también incluye la infraestructura necesaria para ejecutar estas
funcionalidades de forma conjunta. El archivo \id{docker-compose.yml} define
once servicios: el edge, el shell, los tres microfrontends remotos, el API
Gateway, los cuatro microservicios y PostgreSQL. El sistema puede levantarse
mediante \id{docker compose up}, y las migraciones cargan los datos de
demostración utilizados por usuarios, canchas y reservas durante el primer
arranque.

\subsection{Limitaciones}
\label{sec:limitaciones}

Aunque las funcionalidades definidas en el alcance están implementadas, la
versión actual del sistema todavía presenta algunas limitaciones:

\begin{itemize}

    \item \textbf{Los listados no tienen paginación.}
    Los endpoints de usuarios, canchas y reservas devuelven las colecciones
    completas. Para el volumen de datos utilizado en el proyecto esto no genera
    problemas, pero si la cantidad de registros aumenta sería necesario
    incorporar paginación.

    \item \textbf{Parte de los reportes se calcula en memoria.}
    \id{ms-reportes} obtiene la información desde \id{ms-reservas} y
    \id{ms-canchas} mediante sus APIs y realiza los conteos y agrupaciones en
    \id{ReportService}. Con este enfoque se mantiene la separación de datos
    entre los microservicios, aunque el servicio debe obtener y procesar los
    registros necesarios para cada consulta.

    \item \textbf{No se mantiene un historial de activación de las canchas.}
    Para calcular la ocupación de un período se utiliza el horario actual de
    cada cancha. Si una cancha estuvo inactiva durante una parte del rango
    consultado, esos días no pueden identificarse de forma independiente,
    porque \id{canchas_db} conserva únicamente su estado actual.

    \item \textbf{Algunas pruebas necesitan PostgreSQL disponible.}
    Las pruebas de arranque de \id{ms-usuarios}, \id{ms-canchas} y
    \id{ms-reservas} utilizan Testcontainers, por lo que requieren Docker para
    ejecutar PostgreSQL durante la prueba. Además, \id{ConcurrenciaReservaIT}
    necesita una instancia de PostgreSQL configurada mediante
    \id{RESERVAS\_IT\_DB\_URL}. Las pruebas unitarias de los servicios de
    aplicación pueden ejecutarse sin levantar esta infraestructura.

\end{itemize}
